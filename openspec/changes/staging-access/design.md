## One application per staging hostname

Every staging boundary this inventory names is exactly one live hostname: gerry's staging Worker routes marketing paths of one hostname, and its retired `staging.gerry.ejmlabs.com` is a leftover alias, not a second boundary. Cloudflare permits one application to name several destinations and leading wildcards such as `*.example.com` can appear in them, but a wildcard in the middle (`staging.*.ejmlabs.com`) is not a supported form and no site needs a whole-zone match, so the rule collapses to one application per staging hostname. One application per hostname preserves per-worker revocation and keeps each application's audience tag separate, which the agents site verifies against from its Worker (`ACCESS_AUD` in the v0 plan).

## One service token for CI, held only as environment secrets

One Access service token serves every CI smoke and post-deploy check, staging and the gated production agents host alike; per-token-per-application duplication buys nothing and doubles the rotation work. The owner created it on 2026-11-01 as `ejm-agents-deploy-checks` (Zero Trust, Access, Service Tokens), keeps the Client ID and the one-time Client Secret, and no repository text ever records either value.

- Lifetime, decided 2026-11-01: a long-lived token with no expiry and 24-hour Access sessions; `docs/operations.md` records both (task 1.6).
- Each new staging application's policy carries an Include rule for this service token, alongside the owner's email; the owner's agents application already carries its Service Auth policy.
- Storage: the Owner-run script (task 1.4) creates or repairs the `staging` environment in every site repository with the existing main-only branch policy and hands both values to `gh secret set --env staging` on standard input, the same pattern `set_deploy_token.py` already uses. That script stays separate rather than gaining a service-token mode because its flow verifies the deploy token against Cloudflare, a step with no service-token equivalent, and its production-safe defaults should stay untouched. Secrets are GitHub environment secrets named `CF_ACCESS_CLIENT_ID` and `CF_ACCESS_CLIENT_SECRET`, never repository or organization variables or Actions-level secrets. They are written to `staging` by default, because production hosts keep their public posture, and to `production` as well where a production host is gated: the owner set both secrets in the ejm-agents `staging` and `production` environments on 2026-11-01, and the script (task 1.4) covers the other site repositories' `staging` environments.
- The headers the pipeline then sends are `CF-Access-Client-Id` and `CF-Access-Client-Secret`. The projection never falls back to reading the values from anywhere else, and no log line, error message, artifact or test prints them. The value never enters a prompt; the script's error output names a field, never a value. The token is CI-only: it lives only as the pipeline's environment secrets, and agents never hold, fetch or are asked for the values.

What stays unreachable to CI without the token: every path on a staging host, hashed assets included, answers the Access login instead of the page, and unauthenticated CI reads of staging are impossible by design. The deploy itself needs no host reach; Wrangler talks to the Cloudflare API. The per-repo terminal checks that compare staging asset bytes with `dist/` stop working and move to the headed browser or the token headers (task 3 items).

## Smoke and verify checks in the deploy jobs

`scripts/deploy.py` gains a `verify staging` mode for the staging job, after `wrangler deploy` succeeds and inside the same job so the job fails rather than leaving an unverified deploy.

- The mode re-reads the reviewed Wrangler config (already checked out and byte-compared) and takes the staging hostname from `env.staging.routes`: it accepts exactly one custom-domain entry whose pattern is one hostname with no scheme, no path and no wildcard. Anything else fails with a message that names the config field, so gerry's path-pattern routes and future multi-route configs are caught rather than silently skipped.
- It sends GET `https://<staging-host>/` twice (fixed 15 second timeout, no redirect following, body cap bounded like the other reads in this script, `MAX_API_BYTES`): one request with the two headers taken only from `CF_ACCESS_CLIENT_ID` and `CF_ACCESS_CLIENT_SECRET`, which must answer 200 with an HTML content type, and one wrong-secret probe carrying the stored `CF_ACCESS_CLIENT_ID` with a fixed invalid Client Secret (never the stored one), which a gated host must answer with Access's own rejection, an Access-issued 403 or the Access login redirect. The probe carries the Client-ID header the owner's bot-skip matches, so the bot phase exempts it and its answer is Access's or the origin's: Access rejecting the wrong secret proves the gate present and proves the skip did not bypass Access, and the page answering instead proves the gate absent.
- Fail, telling the operator which of these happened, with no environment values printed: the two secrets missing (message points at the owner setup in `docs/operations.md`). On the token request: a redirect to the Access login (the token was absent, wrong, or its policy rule is missing from this application), a Cloudflare challenge (`cf-mitigated` present: the bot phase answered because the skip is absent or does not cover this request), a non-200, or a body over the cap. On the wrong-secret probe: the gate absent (the page answered 200 where Access's rejection was required: the application is missing, deleted, or does not cover the hostname), the challenge on the probe (the skip is mis-scoped or absent; a challenge is never the gate being present, per verify.md's rule that a challenge says nothing about the deploy), or Access's denial absent (any other unexpected answer, such as a non-200 or a body over the cap).
- Fail closed everywhere: there is no flag that skips the check, no environment variable that switches it off, and no widening of the Access boundary to make it green: no bypass application, no allow-list entry besides the owner's email rule and the one smoke service token, no wider path scope, and no bot or WAF exception matching anything besides the smoke token's Client-ID header, value or presence, on the staging hostnames and the two agents hosts. If a site's staging cannot pass, the owner fixes the Access or bot-phase setup and records the decision; the pipeline never self-silences.
- Production jobs on public production hosts gain nothing: their checks remain the headed-browser live checks the deploy skills already describe. A production job whose host sits behind Access, today the agents host under the owner's application, runs the same two-read verify against the production hostname with the token values taken from that job's environment secrets (`production` for a production deploy), the same failure kinds and the same fail-closed rules.

## The zone's bot phase is a design input

The zone's Super Bot Fight Mode challenges automated clients on HTML routes: the 2026-10-26 account snapshot records `sbfm_definitely_automated: managed_challenge`, [verify.md](../../../templates/agents/skills/ejmlabs-cloudflare/references/verify.md) documents curl and headless reads of the ejmlabs HTML routes answering the 403 "Just a moment..." page and says not to count that as a pass or a deploy failure, and a 2026-11-01 re-probe reproduced it (default curl answered 403 `cf-mitigated: challenge` on every staging root where a browser User-Agent answers 200; `relay.ejmlabs.com` answers its own 401 because the zone's existing "Skip SBFM for machine clients" rule exempts it). A GitHub runner's Python GET is exactly the class that phase challenges. The remedy is owner-only and Access-boundary scoped, with its match form pinned, and the owner decided it on 2026-11-01 (`staging skip`): a bot-management skip matching the smoke service token's `CF-Access-Client-Id` header, its exact value or its presence (the Client ID is the non-secret half, safe to name in a rule), applied only on the gated hosts this plan's smoke reads, the staging hostnames the new applications cover and the two agents hosts (the production order of the same day puts a verify on `agents.ejmlabs.com`, whose probe needs the same exemption), never host-wide or path-wide and never zone-wide beyond those hosts, so a leaked token skips nothing else; the owner applies the skip and records it with its expression in `docs/operations.md` (owner actions in the report). The wrong-secret denial probe relies on exactly this match: it presents the same Client-ID header the skip matches, so the bot phase exempts it and Access itself must answer. Until the skip is applied, a challenge on the token request or the probe fails the smoke and the deploy stays blocked; a challenge is never a pass and never the gate. If the skip does not clear the smoke live, the follow-up change moves the smoke target to a per-site path the zone serves machine clients without a challenge (the verify.md precedent of `robots.txt` and hashed `/assets/*`), trading page verification for build-served verification, as a new owner decision.

Config parsing reuses the existing `site_config` reader; the smoke adds no new dependency and no second URL source. The `ejm-agents` staging Worker sits behind the same gate, and the v0 plan's server-side JWT audience check continues to run after Access at the edge, so a green smoke says the build is served through the gate and the gate is present.

## Profile wiring for `ejm-agents`

The v0 approvals order the profile after the site lands. `scripts/standards.py` adds an `ejm-agents` profile with `deploy=True` (which adds it to `SITE_DEPLOY`), and `scripts/deploy.py` adds its `SITES` entry: commands from the product's own build, `wrangler.jsonc`, and the paths the deploy needs, including the Worker source and `container/` because Wrangler builds its image from that source during deploy. `standards.py` accepts the caller only in the canonical form, so `ejm-agents`' local workflow is replaced by the shared caller in the same PR that moves its pins. Nothing in this change hides the containers permission the deploy token needs for that site; the v0 approvals already ask the owner to widen the token for containers and verify the dashboard label, and the smoke step changes nothing about the token.

## What this change deliberately does not do

- No Cloudflare action by the pipeline or an agent. Every Access application, rule, service token and secret add is an owner action listed one by one in the report.
- No new production Access from this repository's changes. The owner gated the agents production host himself on 2026-11-01, and this change plans only its CI token path and verify; other production hosts stay public; chess's existing whole-host application and gerry's staging boundary stay as they are.
- No per-repo implementation here. Each repository's docs and caller fixes list in `tasks.md` and land one PR per repository.
- No bypass for webhooks or unauthenticated traffic. gerry's per-path webhook bypasses keep their current per-path scope; nothing admits an unauthenticated request to a staging host; the one bot-phase exception is the owner's recorded, token-scoped decision in the bot phase section above.

## Limits recorded

- The Cloudflare state in this design comes from repository files at the listed commits, the account snapshot of 2026-10-26 (`/workspace/cloudflare-review/applied-2026-10-26/`), gerry's Access documentation, unauthenticated GET probes on 2026-11-01, and the owner's own relay of that day (application `847b7650` on the agents hosts, service token `ejm-agents-deploy-checks`). No Access or API listing was read with credentials in this task, so the remaining application IDs stay the historical record's names and the owner confirms live IDs in the dashboard as he creates each application.
- The zone's bot phase is recorded above as a design input: it challenges automated GETs of HTML routes today, the owner's token-scoped skip decision remediates it inside the Access boundary, and whether a token-carrying GET answers 200 under it is unverified until the owner's first token-carrying check or the first live smoke.

## Risks

- Every staging smoke stays red until the owner applies the decided bot-phase skip and the per-application token rules: the fail-closed design makes the deploys wait on the owner's Cloudflare actions, and the failure messages name the missing piece so the wait is legible.
- A rotated or revoked token blocks every site's deploy at the smoke step until the owner re-stores the values; the long-lived token with no expiry is the decided trade, and rotation is a pure secret update with no code change.
- A staging hostname renamed or dropped in a Wrangler config without its Access application turns into the gate-absent failure kind at the next deploy, which is the hazard working as intended; the drift still requires a reviewed change before the next deploy.
- The media host's move behind the proxy is decided but unproven: LiveKit media and TURN must still traverse Cloudflare's proxy, and if they cannot, the owner records the fallback posture as a new decision rather than the pipeline weakening anything.
