# Design: two-lane PR governance

## Context

Today every PR in the seven public repositories passes one gate (`scripts/governance.py`, generated into `.github/workflows/governance.yml`, called from each repository's `pr.yml` on `issue_comment`):

1. A human with maintain/admin posts `/ready <40-char head SHA>`. Admission checks role, exact head, non-draft, `main` target, unedited comment, first run attempt and limits (200 files, 12,000 lines, 1 MB diff), and consumes the comment once.
2. Trusted preparation archives the head as data. Quality, registry, standards and two serial automated review passes run. Each pass has a 9-minute step inside a 12-minute job. Critical/high/medium findings block, and an incomplete result fails.
3. `/approve <SHA>` records a bot approval and a `Maintainer approval` status. `/revoke <SHA>` fails both and cancels the run. Edited or deleted decisions revoke too.
4. Branch protection requires five strict statuses from the GitHub Actions app and one approval. Squash only, auto-merge off.
5. `scripts/release.py` accepts a release commit only if it is the merge of one PR whose head carries the five statuses and unedited `/ready` and `/approve` comments, and whose tree equals the release tree.

The gate is sound, but every new commit costs two SHA copies and a full paid review. Quota or timeout failures have no defined outcome, and docs edits pay full price. The owner wants one action per merge with no SHA and few re-runs. The repositories are public, so slop and abuse must still be kept out.

Facts this design relies on:
- Commit statuses and checks attach to a **commit SHA**, not a PR. A green check on a SHA is visible to every PR, base and push generation that has that SHA. PR-specific authority therefore has to live outside commit checks.
- A status published by the GitHub Actions app cannot prove which workflow published it. Any writer can add a branch workflow, and a branch workflow can request any secret that its repository or environment exposes to its ref.
- `pull_request_review` and `pull_request` workflows run from the PR's own merge ref, so a same-repository author controls their code.
- Repository writers can edit and delete other people's comments, and can add and remove labels. Comments and labels cannot hold authoritative state.
- A PR author cannot natively approve their own PR.
- Public repository logs and artifacts can be read by anyone.

These items must be **verified during preflight** rather than assumed: plan support for organization rulesets, for rulesets on private repositories, and for restricting `main` updates to one App; check-run button behaviour; the current GitHub policy for `pull_request_target` and fork-run approval in each repository; and the merge endpoint's expected-head parameter.

## Goals / Non-goals

**Goals**: one action per trusted merge, with no SHA typing. Automatic review that does not re-run needlessly. A cheap path for inert docs. A defined, visible outcome when the reviewer is unavailable. No secret, paid job or publication credential reachable from PR-controlled code. Authority that cannot be replayed across PRs or pushes. Every decision auditable.

**Non-goals**: changing the review rubric or blocking severities. Package publication and deployment. Private product repositories.

## Architecture: an App-held control plane

```
GitHub webhooks ──▶ Governance service (holds Governance App key)
                    ├─ per-PR serialized decision log (authoritative state)
                    ├─ push ledger, quarantine list, budget ledger, audit store
                    ├─ publishes App check runs + one required "Governance" check
                    ├─ dispatches (Runner-dispatch App) ──▶ governance-quality (public, main only)
                    │                        ├─ Quality on PR code (no secrets, no id-token, conclusion only)
                    │                        └─ standards job (PR tree as data, own tooling)
                    ├─ dispatches (Runner-dispatch App) ──▶ governance-review (private, main only)
                    │                        ├─ paid review on the diff as data (environment secret, no id-token)
                    │                        └─ result job (runs no PR code) ── OIDC-signed bound payload
                    └─ performs every merge (merge permit + intent, expected head, serialized per repo)
```

- **Governance service**: a small web service that receives the Governance App's webhooks, holds the App private keys, and keeps all authoritative state in its own durable store. It is the only component that can publish governance checks, push protected namespaces, merge PRs or spend review budget. It runs on the lab's existing edge/serverless hosting provider inside an enforced $25-per-month envelope (decision 5); its trust root is defined below. The state store must support per-PR serialization (compare-and-set on a version number) and append-only audit records.
- **Quality runner** (`ejmlabs/governance-quality`, public): runs Quality and registry on PR code, dispatched to its protected `main` by the Runner-dispatch App. Every job that runs PR code has `permissions: {}` except `contents: read`, no `id-token`, no artifact upload and no environment. PR code can still save a cache through the Actions runtime token, whatever `permissions:` says, so **no job in the quality runner restores a cache**. Repository standards and the Markdown checks run in their own job, which installs its tooling first and then reads the PR tree as data, never executing PR code. Quality results are posted by a separate job that runs no PR code and reads only job conclusions. Public logs and free minutes are fine here.
- **Review runner** (`ejmlabs/governance-review`, private): runs the paid review. It never checks out or executes PR code: it reads the diff as data, restores no caches, downloads no artifacts, and installs the reviewer from a hash lock. The key is `MODEL_API_KEY` in the `review` environment (a different key, and a different name, from any key held by a product repository during migration), whose deployment policy is "selected branches" with exactly `main`. The job holding the key has no `id-token`. Because this runner runs no PR code, the review job may pass its bounded result file to the result job through job outputs; the result job posts it with its OIDC token, bound to the dispatch id, run id, generation, head, base, pass and payload digest. The service requires both that payload and the review job's success; anything missing, skipped, cancelled or malformed is never `passed`. Its workflow source may be mirrored publicly; its output stays private. It relies only on GitHub Team features (see "GitHub Team plan and the private review runner").
- Both runner repositories: writers are the owner, the `security` team (code ownership needs write) and the Governance App; ruleset B still stops anyone but the Governance App updating `main`. Changes go through this governance as release-affecting. GitHub-hosted ephemeral runners only (self-hosted runners are banned in org policy for every governed and runner repository). The Maintainer-agent and Chief of Staff Apps are never installed on them. Separate repositories give separate cache scopes and separate OIDC `repository_id` values.
- **Product repositories** hold **no secrets** once migration finishes: no repository or organization secrets exposed to them, no environments with secrets, and no publication credentials. During migration there are exactly two enumerated, per-repository, time-boxed exceptions (see "Migration phases and secret exceptions"): the old provider key until that repository's re-pin, and the switch's key in a `legacy-review` environment from the key's addition after that repository's S re-pin until cutover or the phase-B expiry. After cutover the rule is unconditional. Until then, paid review also runs, isolated, in the legacy replacement job (see Migration); the "paid review only in the private runner" rule applies per repository from cutover. They keep a community CI caller (`pull_request`, `permissions: {}` except `contents: read`, no secrets) for contributor feedback. That CI is informational and never gates a merge.

So no PR-controlled workflow can reach a credential that matters. Authority comes from webhooks and API reads made by the service, never from workflow outputs on PR refs.

**Result verification.** The service accepts a runner result only if its OIDC token passes every check: `iss`; a service-specific `aud`; `repository_id` and `repository_owner_id` (ids, not names); `job_workflow_ref` including the workflow path, mapped one-to-one to the result type; `ref == refs/heads/main`; `event_name == workflow_dispatch`; `run_attempt == 1`; `run_id` equal to the run recorded for the dispatch (correlation by a dispatch id echoed in `run-name`, proven in preflight); single use of `jti`; and `exp`. Review results also need the bound payload and its digest.

**Banned triggers.** Governed repositories MUST NOT use `pull_request_target` or `workflow_run`; `standards.py` fails on either.

**Branch workflows confer nothing, and cannot publish.** Any writer can push a branch whose own workflow files run on `pull_request` or `push` with no approval. Such a run finds no stored secret, but it always gets the built-in `GITHUB_TOKEN`, and an explicit `permissions:` block can raise that token up to the repository's maximum. No setting stops that, so the design removes the publication paths themselves rather than relying on downstream rejection:
1. Nothing the token writes counts. The only required check is `Governance`, bound to the Governance App's integration id; the service never reads statuses, checks, comments or labels back as state.
2. Rulesets on `main`, `contrib/**` and `workflow-pins/*` block the token, and a ruleset on **all tags** restricts creation, update and deletion to the governed release actor. A tag ruleset governs tag refs only: it does **not** stop asset uploads, edits of an existing release, draft releases, a release created on an existing tag, or package publication. Those are handled by items 3 to 5.
3. **No agent credential can publish.** The Maintainer-agent App holds **no `contents: write`** (which is what authorizes release and asset operations), no `workflows` and no `packages` permission. Agents write branches only through the service's **branch broker**: the agent submits commits for an `agent/**` branch over an authenticated service API; the broker computes refusals from the full resulting tree diff against the target branch (never from client-supplied paths) and refuses any change under `.github/workflows/**` or `.github/actions/**`, symlinks or submodules anywhere, renames into those paths, any tag ref and any non-`agent/**` ref; pushes with a Governance App token scoped to that repository, and records the agent App as the pushing principal in the push ledger. The broker exposes no release, tag, asset or package operation.
4. **Existing releases and assets**: immutable releases are enabled in every governed repository, so a release published after enabling cannot have its assets or tag changed; only the governed release actor creates and publishes releases. Immutability is expected to cover only releases published after it is enabled, and drafts stay mutable, so preflight inventories existing releases (republished or accepted on the record) and tests deleting an immutable release and recreating one on the same tag with a branch token; governed releases carry attestations from the governed release actor so consumers can tell them apart. **Packages**: no product repository uses a package namespace, and no agent credential holds `packages: write`. GitHub's organization package settings limit visibility rather than restricting creation to one actor, so preflight verifies what can be denied; a trusted human's branch workflow publishing a package is part of the decision-14 residual below.
5. **Workflow token ceiling**: in a product repository, no workflow on `main` triggered by `pull_request` or `push` requests any permission beyond `contents: read` (a standards check), and the org default token is read-only. Branch runs execute `main`'s workflow files when the branch does not change them, and an agent branch cannot change them (item 3).
6. No external OIDC trust (cloud, registry or the service) accepts a product-repository token, with one narrow, dated exception: the service accepts the legacy reservation job's token for **reservation grants only, never a result** (see Migration). Otherwise only runner-`main` tokens are trusted.

Preflight shows each of these calls is **denied** at GitHub for every agent credential and agent-pushed branch run: release creation on a new and an existing tag, draft release creation, asset upload, deletion and replacement on an existing release, and package publication. Residual risk: a trusted human, or a stolen maintainer session, can still write a branch workflow that raises its own token and creates a draft release or a release on an existing tag, or publishes a package; immutable releases stop it changing a published release. That is the accepted compromised-maintainer risk (decision 14); org audit-log streaming alerts on every release and package event.

The service takes over the existing safeguards: first-attempt-only runs, a live re-read of every decision, an edited or deleted command revokes, and bounded metadata pages. The admission code in `scripts/governance.py` is ported into the service, not discarded.

### Service trust root

Whoever controls the service controls `main` everywhere, so its trust root is fixed here:

- **Source and deploy.** The service source lives in a public governed repository, listed in the release-affecting policy file. It deploys only from protected `main`, through workload identity (OIDC); non-OIDC deploys and long-lived provider API tokens are disabled. A deploy needs the owner's ship plus a code-owner review from a `security` member who is not the owner, enforced by ruleset with no bypass, not by environment reviewers. No human gets shell access to production.
- **Security role.** `security` team members are humans whose tokens no automation holds, and the owner is not one of them: GitHub accepts any code-owner team member's approval, so an owner in `security` could satisfy the backstop and the most-recent-push rule alone. Preflight reads the membership back, and the hourly reconciliation re-reads it: if the owner, an App or an automation account is a member, merges freeze on `.github`, both runner repositories and the service repository and the owner and the security lead are alerted, until the membership is corrected and read back. The hour is not the only check. A `membership` webhook event on `security` triggers the same re-read and freeze at once, and at every backstop merge permit the service re-reads that none of those accounts is a member and that the approving security reviewer is a listed human other than the owner, refusing the merge otherwise. As an org owner the owner can still change membership; these checks catch it before the next backstop merge. This is a **hard prerequisite** for preflight and cutover: independent security approval, the code-owner backstop and the two-person service deploy cannot be satisfied by one person, and a recorded single-person acceptance does not pass preflight. An automated reviewer never counts as the second human. If the owner wants a single-person alternative, it must be defined as a separate policy with consistent enforcement before rollout.
- **Hosting account** (decision 5): the lab's existing edge/serverless hosting provider. Its administrators are listed and use hardware-key two-factor authentication; its audit log streams to the audit store; an hourly check compares the running build hash with the build of the service repository's current `main`, and a mismatch freezes merges and alerts. A single hosting administrator is a recorded accepted risk.
- **Hosting cost envelope**: hosting, storage, queues and logging sit inside a provider-enforced budget or fixed-price envelope of at most $25 per month, with bounded ingress (unsigned requests rejected at the edge before any work, request-rate limits) and alerts. Exhausting the envelope stops authorizations and merges, never passes them. Whether the host can enforce this, sign with a non-exportable key, and accept OIDC deploys is **unverified**; if it cannot, the limitation returns to the owner before rollout.
- **Key custody** (decision 13, security lead answer B2), for the Governance App and Runner-dispatch App keys:
  - Each PEM is imported as a non-exportable RS256 signing key and the downloaded PEM is destroyed; failing that, it sits in the host's managed secret store with access only from the runtime identity. Never in GitHub Actions secrets, a repository, a laptop or a log. The webhook secret gets the same treatment.
  - Only the runtime identity can sign. Changing the key policy needs both the owner and the security lead. No human signs ad hoc; break-glass access is time-boxed and alerts.
  - Rotation every 90 days, and at once on suspicion or on staff or host change: generate key 2, import, deploy, verify token minting, delete key 1 within 24 hours. The owner approves every rotation and deletion.
  - Revocation runbook (rehearsed in the pilot): kill switch and merge freeze; delete the compromised key; suspend the installation to cut live tokens; rotate the webhook secret; quarantine every open PR; review the org audit log and signing logs for the exposure window and diff `main` and `contrib/**` against merge records; re-key, then unfreeze.
  - Audit: signing logs, the org audit log (streamed where the plan allows; on Team, the replacements and the owner's web audit-log review in "Detection on GitHub Team" below) for App key create and delete, installation and ruleset changes, bypass use, releases and packages, a service log of every token mint (repo, permissions, purpose; never the token), and the weekly report.
- **Webhooks.** Verify `X-Hub-Signature-256` in constant time; reject unsigned requests; keep delivery ids for the retention window and process each once (payloads are triggers only, so a replay after expiry changes nothing); re-fetch PRs, comments, reviews and the check-run `requested_action` sender through the API before acting. A `requested_action` counts only on a check run whose `app.id` is the Governance App and only from a trusted human sender; anyone else is refused and audited.
- **Missed events fail closed.** If the live head differs from the ledger head, the service starts a new generation with an unknown pusher, puts the PR in the outside lane until reconciled, and refuses ship. The hourly reconciliation includes PR heads.
- **Tokens.** Installation tokens are minted per operation, scoped down with the `repositories` and `permissions` parameters, held in memory only for at most their 1-hour life, and never logged. One App has one installation per organization, so dispatch is split out as a separate **Runner-dispatch App** with its own key, holding only `actions: write` and installed only on the two runner repositories; the Governance App holds no `actions` permission. The Governance App is installed on the seven product repositories, both runner repositories and the service repository, and every token is scoped down to the one target repository. The review workflow refuses to run, before the key enters any step, unless the triggering actor is the Runner-dispatch App's bot; usage read back from the provider that matches no dispatch is settled into the ledger and alerted.
- **Independent backstop.** On `.github`, both runner repositories and the service repository, a GitHub-native ruleset requires code-owner review from `@ejmlabs/security` with no bypass, **dismisses stale approvals on every push, and requires approval of the most recent reviewable push** by someone other than its pusher, so a compromised service alone cannot change governance. CODEOWNERS makes `@ejmlabs/security` the **sole** owner of every governance path (`.github/`, `scripts/`, `review/`, `templates/community/`, the staged `templates/community-next/`, `tests/`, `openspec/`, `docs/operations.md`, the root community files, `VERSION`, `RELEASING.md`, `.gitignore`, `.gitattributes`); maintainers own only the `*` fallback, which intentionally leaves them `LICENSE`, `README.md` and `CHANGELOG.md` (no governance rule lives there). This list is `.github`'s. Both runner repositories and the service repository carry runner or service source outside these prefixes, so there `*` is owned by `@ejmlabs/security` alone and maintainers own nothing; otherwise that source would fall to maintainers and a maintainer-only code-owner approval would satisfy the service's two-person deploy rule. Listing both teams on one path would let either satisfy review, so a test walks every file (one machine-readable module, `scripts/governance_paths.py`, holding one list per backstop repository kind, read by the test and by the future standards check) and checks that its last matching rule names the security team alone, including a mutation case with an overriding rule; the same check, with each repository's own list, moves into standards for every backstop repository, and preflight reads `codeowners/errors` back empty. Both teams must exist with write access before that CODEOWNERS change takes effect, because GitHub silently ignores an invalid owner and would leave the path with no code owner. The `security` team has write on those repositories so its code ownership is valid; ruleset B still stops direct merges. Preflight reads these settings back and proves (a) an owner, maintainer-only or App approval of a governance file, with every service check green, is rejected without an independent security review, and (b) after a security approval of head H, an App push of H2 with every service-owned check green is refused by GitHub until a fresh security review, including on the private runner.

### GitHub Team plan and the private review runner

The lab is already on GitHub Team (decision 12; no new cost, one seat needed since Apps and `GITHUB_TOKEN` use no seats). On Team, private repositories get environments, environment secrets, deployment branch and tag restrictions, and rulesets. Required reviewers, wait timers, custom deployment protection rules and blocking administrator bypass of environment rules are **not** available for private repositories on Team (they need Enterprise).

Check of this design against that list:
- The `review` environment uses only an environment secret and a "selected branches" deployment policy of exactly `main`: supported.
- No environment in a private repository uses required reviewers, wait timers or custom deployment protection rules. All human approval lives in the service (ship, security approval) and in rulesets. The two-person deploy rule for the service is a ruleset rule in a public repository.
- **Administrator bypass cannot be blocked** on the private review runner. The design does not rely on blocking it: the review runner's only administrator is the owner (no App or agent holds administration write, and no agent holds the owner's token, decision 11, except the named exception for the `ejm-ui` switch lift and restore until 2026-11-20; that exception's credential is a fine-grained token limited by GitHub to `ejm-ui`, so it does not reach this repository); the service accepts results only through the checks above, so a bypassed run cannot produce an accepted result; and the hourly reconciliation flags any `review` deployment that matches no recorded dispatch. Residual risk, accepted on the record: the owner, as administrator, could read `MODEL_API_KEY` through a bypassed run. The owner is also the only administrator of the provider team that issues that key.
- Rulesets on the private review runner (`main` requires the Governance check and code-owner review; only the Governance App may update) use Team-supported ruleset features; preflight reads them back.

No part of the design depends on an Enterprise-only feature. Organization audit-log streaming, which this design uses for detection in several places, is documented by GitHub as an Enterprise Cloud feature, and on Team the org audit log can be neither streamed nor read through the REST API. So on the lab's plan the replacements below are the expected case, not a fallback; preflight item 1 reads back which source works and that each replacement event is delivered.

**No App or agent holds administration write** (owner, 4:35 PM PT: the restore-only App considered at 4:06 PM PT is dropped). **One named, owner-accepted exception to decision 11** (owner, 4:53 PM PT): the lab's automation runs the `ejm-ui` switch-exception lift and restore with the owner's GitHub administrator account, until 2026-11-20 at the latest (Migration, "Named exception to decision 11"). The owner credential is a fine-grained token limited by GitHub to `ejm-ui`, held only by the automation's restore runner, a deterministic process with no model in its loop. The orchestrator is an agent and reads untrusted `ejm-ui` PR content; it never holds the credential and can only ask the runner for allowlisted operations, but through the runner the automation still acts with the owner's administrator rights on `ejm-ui`. A switch-exception lift or restore on any other repository is done by the owner in person.

**Who checks for administration-write credentials.** App installations and their permissions: the Governance App's organization administration read (installation inventory). Users with an admin role on any repository and org owners: the owner's settings tool (task 1.12), run by the owner. Org fine-grained tokens with administration write: the owner, reading the org's fine-grained token list in the web settings (the listing API is open only to a GitHub App with the organization personal-access-token permission). Classic tokens, OAuth grants and App user tokens cannot be listed on Team: the quarterly credential review and the owner's web audit-log review cover them. The exception credential is recorded by the owner when it is issued, not discovered; during the exception it is the only expected finding, and any other finding fails preflight and is alerted.

GitHub cannot grant contents write "on branches only". Ref limits are enforced by rulesets. On `main`, **ruleset A** (PR required, `Governance` required from the Governance App's integration id, squash only, linear history, conversation resolution, no force push or deletion, **no bypass actors**) and **ruleset B** (restrict updates, with the Governance App as its only bypass actor). Ruleset B is a hard preflight gate: no cutover without it. Putting the App on ruleset A's bypass list would bypass every rule, so it never is. On `contrib/**`, ruleset A only forbids force push and deletion, and ruleset B restricts creation and update to the Governance App; both are read back. The `workflows` permission lets the service merge PRs that change `.github/workflows/*`, and is itself release-affecting.

The preflight acceptance suite (decision 13, security lead answer B1) is the table below. The pilot re-runs it on `.github`; every row must fail closed.

| # | Attack | Expected result |
| --- | --- | --- |
| 1 | Fork PR edits workflows, `outside-ci.yml`, `CODEOWNERS`, the governance profile or the `REPOS` list | Outside lane; triage fails; community CI runs with a read token and no secrets; no paid work |
| 2 | Same-repository branch from a compromised writer adds a workflow requesting secrets, `id-token: write` or `contents: write` | No secrets exist; its OIDC token is rejected; outside lane if the pusher is untrusted |
| 3 | Agent App or maintainer calls the merge API, or pushes to `main` or `contrib/**`; a branch token posts a `Governance` status or check | Ref updates and merges denied by rulesets A and B; a posted status or check may be created but changes no service state and does not satisfy the integration-bound required check |

## Decision log

Each PR has an append-only, versioned log in the service store. Events are processed one at a time per PR, using compare-and-set on the log version. An event whose version precondition fails is re-evaluated against fresh state, never applied blindly. Key fields:

- `generation`: incremented on every head change (push, force push, H→X→H counts twice), every base change or retarget, every close/reopen, and every ready↔draft transition. Each generation records when it began.
- `epoch`: within a generation, advanced by `/unship`, `/restore-lane` and every other revocation. Each revocation writes a **tombstone** and an **epoch boundary time**: the later of the GitHub-assigned event or delivery time (for example the `/unship` comment's `created_at`) and the service receive time. Commit, author or `head_commit` timestamps, which a pusher sets, are never used. Generation start times follow the same rule.
- **Action time**: every human authorization is bound to the epoch in force when the human acted, judged from a GitHub-assigned time that the actor cannot set: a check-run click by its action record, a native review by `submitted_at`, a comment by `created_at`. An authorization counts only if its action time is at least 60 seconds after the latest epoch boundary of its generation (the margin covers clock and delivery skew). Earlier or ambiguous ordering is rejected, never assigned the epoch current at handling time. This applies equally to authorizations the service never saw before the revocation. A channel that cannot give such a time is disabled and the reply offers the current button.
- **Action records**: each `Ship`, `Security review` and `Adopt` check run is created for one immutable record `(repo, PR, head, base, generation, epoch)`, and is replaced when the epoch or generation changes. A click counts only if its check-run id maps to the current record. A native review counts only if it was submitted after the current generation began, and each review id counts at most once; a tombstoned review id never counts again.
- `lane`, `quarantine` flags and `adoption` provenance.
- Authorizations: `ship`, `security_ok`, `waiver`, each with actor id, action record, generation, epoch, head and base.
- Results: `quality`, `review` and `merge_validation`, keyed by `(repo, pr, head, base sha, policy version, pass)`; merge validation also by the proposed merge tree.

The **push ledger** records, for every head the service sees, the webhook's authenticated `sender`, its delivery time as received by the service, and the head and before SHAs. It is the only source of "who pushed". Commit author and committer strings and co-author trailers never grant or remove authority.

The sender does not always identify the credential: GitHub attributes a deploy-key push to a user (the account that added the key), not to the key. So product repositories have **no deploy keys with write**. A write deploy key is a finding that fails preflight, and while one exists every PR in that repository is outside and ship is refused. The service trusts a sender only for push kinds whose real payloads were captured in preflight acceptance tests (user token, Governance App token for adoption and branch-broker pushes; the broker's own record names the agent principal). Where provenance cannot be established, the push counts as untrusted.

Comments and labels are **display only**. The service rewrites them from the log. Removing a label or editing a bot comment changes nothing.

## Lane classification

The service classifies on every relevant webhook from metadata only:

1. **Outside** if any of these holds: the head repository differs from the base; the author is not trusted; any push-ledger sender for the PR is not trusted; the author or any sender has an open access finding (see settings); the repository has an open deploy-key or App-inventory finding; the PR, principal, head or tree is quarantined; or the head branch is in `contrib/**` but the head lacks a matching adoption record. A same-repository head is never trusted for its location: it passes only through the principal checks, like any other PR.
2. **Inert** (the old "fast lane") if the PR is trusted, not adopted, and every changed file passes the inert rules below.
3. Otherwise **trusted**.

The `Lane` check run shows the result for people to read. Nothing reads it back.

### Inert docs lane

The default rules are strict. A profile can only narrow them; widening needs a reviewed policy change:

- Allowed file types: `.md` and `.txt` only, as regular files (mode `100644`). Symlinks, submodules, executables, binaries and other modes are not allowed.
- Paths are normalized, case-folded and NFC-normalized before matching, and extensions match case-insensitively (`.MD` is `.md`).
- Allowed locations: the profile's explicit documentation directories and root community files, minus anything a docs site or build consumes. For example, `ejmlabs` site sources and `ejm-ui` package docs are never inert.
- Never inert, whatever the location:
  - active `.txt` files: `requirements*.txt`, `docs/requirements.txt`, `constraints.txt`, `robots.txt`, `CMakeLists.txt`, `llms.txt`;
  - files that instruct agents (prompt-injection carriers): `AGENTS.md`, `.github/instructions/**`, `*.prompt.md`, and every tool-specific agent instruction file or directory, listed by exact path or glob in the versioned policy file (which is configuration and exempt from the naming check);
  - `.github/**/*.md` (PR and issue templates and other GitHub-consumed files);
  - `README*`, install and release docs (`INSTALL*`, `RELEASING.md`, changelogs and release notes).
- Markdown must be inert: no raw HTML tags, no `<script>`/`<iframe>`/`on*=` attributes, no front matter, no include, directive or Liquid syntax (`{% %}`, `{{ }}`), and no `javascript:` or `data:` link targets. The checker fails closed on anything it cannot parse.
- The diff must not add or change fenced code blocks, URLs or domains, or checksum-like hex strings (Board review): those can change what a reader runs or downloads, so such PRs go to the trusted lane and get the paid review.
- For renames and deletions, both the old and new path must be allowed.
- Config files are never inert. The owner asked for a "docs/config" fast lane, but config affects behavior, so it is deferred (decision 8): a profile may later list specific config files after review.

Inert PRs run `Repository standards` and a Markdown render/link check (both free) and still need a human ship. **Lane and tier stay separate**: inert is a lane; its review cap, pass count, reservation and merge eligibility come only from the PR's effective tier from the classifier. An inert PR over 300 lines is T2 (or T3 over 1,000), and every PR is T3 while the classifier is absent or failing. The automated review may be skipped (G12, under re-review) only when the effective tier is actually T0, the 50-PR shadow is complete and clean, and the owner has recorded the approval; a skip flag never applies to any other tier.

**Centrally owned documents**: `CONTRIBUTING.md`, `SECURITY.md`, `SUPPORT.md`, `CODE_OF_CONDUCT.md`, `GOVERNANCE.md`, `MAINTAINERS`, `RELEASING.md` and `THIRD_PARTY_NOTICES.md` are generated from `templates/community/` and checked for equality by `standards.py`. A local edit to them fails standards by design. To change them, edit the template in `.github`. After that merges, the service opens a sync PR from the Maintainer-agent App in each repository. Those sync PRs need one human ship each, or a single owner "ship all sync PRs" action that the service allows only after confirming each sync diff exactly matches the merged template.

`GOVERNANCE.md` says who can adopt, ship, waive and restore, how someone becomes or stops being a maintainer, how appeals and decisions work, and what governance records are kept (the privacy note). `MAINTAINERS` lists the maintainers and the security team with the role contacts: `security@ejmlabs.com` for security and an org-wide code-of-conduct role alias on the same pattern.

## Trusted lane

### When work runs

On a non-draft trusted or inert PR:

1. After a 2-minute debounce with no new push, the service checks the dedupe key. Metadata-only events (title, body, labels) never start paid work.
2. It dispatches **Quality** and, in a separate job, **Repository standards** to the quality runner, which fetches the exact head and base from the public repository with no credentials.
3. If both pass, it **reserves budget**, then dispatches the paid review to the review runner at the PR's effective tier input cap: 1 pass for a T0 PR, 2 passes otherwise, or 3 for release-affecting PRs. Lane never sets the cap or the pass count. A newer generation cancels the run. A cancelled or failed pass still counts against the budget.
4. Each runner's result job posts to the service with its OIDC token (and, for review, the bound payload), and the service applies every result-verification check above. Stale results (an old generation or dedupe key) are recorded and ignored.

### Ship: binding without a SHA

There are three ways to ship. All of them bind to an exact head, generation and epoch:

1. **Ship button** (primary): each action record's `Ship` check run carries a "Ship this commit" action. The click arrives as a webhook carrying that check run's id; the service accepts it only if that id maps to the current action record (same head, base, generation and epoch) and no tombstone covers it.
2. **Native Approve review** by a human maintainer who is not the PR author and pushed no commit to it: the service re-fetches the review and accepts it if `commit_id` is the current head, its `submitted_at` passes the action-time rule for the current epoch, its review id has not been used or tombstoned, the reviewer's `user.type == "User"`, and the reviewer holds a live trusted role at decision time.
3. **`/ship` comment**, typed by a trusted human whose account no automation holds a token for: accepted only if the push ledger shows the current head was received by the service at least 60 seconds before the comment's `created_at`, no head event was received after it, and its `created_at` passes the action-time rule for the current epoch. The same epoch rule applies to `/security-ok` and `/adopt` comments. If the ordering is uncertain, the command is rejected and the button is offered instead. An optional hex prefix of at least 7 characters must match if given.

On a PR that any App pushed to, or that is release-affecting, a `/ship` comment never counts: the ship must be the button or a native review. Comments from App or bot accounts never count anywhere. For a PR the Maintainer-agent App pushed to, the shipping human's `Signed-off-by` is added to the squash message, because an agent cannot make the DCO certification; the ship action says so.

`/unship`, a dismissed native approval, an edited or deleted `/ship` comment, a new generation, a lane change to outside, and quarantine all revoke immediately, write a tombstone and advance the epoch.

### Merging: performed by the Governance service

The service is the only merger. Steps, serialized per repository:

1. **Merge validation**, for **every** merge including the first attempt: run Quality (free) on the exact proposed merge tree of the head and the current `main`, recorded with that base SHA. A result is reused only while the proposed tree and base are identical. Standards results for the PR's text are bound to a digest of the title, body and trailers; an edit re-runs those free checks (never the paid review). Review evidence is reused only if the PR's own patch is unchanged (same head, and same patch-id against the new merge base); otherwise the change needs review. The owner never has to rebase just because `main` moved. Validation runs without holding the PR's log, so revocations apply during it.
2. **Merge permit**: immediately before merging, under the per-repository merge lock, compose the final squash title and message (including trailers) from a fresh read of the PR, run the free text checks on exactly that text (template, public-history and sign-off), and atomically claim a permit against the current PR log version: re-verify PR open, base `main`, head, generation and epoch unchanged, ship actor still trusted, security approver still in `security` and not the ship actor, no quarantine, no unresolved conversations, no audit backlog, validation current, and the squash-text digest checked. In the same transaction, write a durable **merge-intent** record (PR, head, generation, epoch, validated tree, squash-text digest). Any revocation advances the version and voids pending permits.
3. Set the required `Governance` check to success on the head, then, in one compare-and-set, confirm the permit is still valid; if it is void, set `Governance` to failure and stop. Otherwise merge immediately with **squash, expected head SHA and the validated title and message sent explicitly**, so a later title or body edit never enters history. If the merge fails, set `Governance` to failure. A revocation that arrives after the merge call is issued cannot stop that merge (revocation is prompt, not instantaneous).
4. Record the merged tree SHA against the intent. If it differs from the validated tree, freeze merges in that repository, alert the owner and security lead, and open a revert PR.
5. Post a newer `Governance` check run on the merged head with a non-success conclusion ("merged in #N; not reusable"), and publish the evidence check on the merge commit (see Release validation). A head that already has a Governance record starts pending in any other PR.

On startup and every minute, a sweep sets `Governance` to failure for every intent with no recorded merge, and publishes any missing merge-commit evidence check. Every new head starts with `Governance` pending. So a crash, timeout or deploy between steps 3 and 4 leaves no lasting green SHA, and ruleset B stops anyone else merging during that window.

The `Governance` check is the only required check. Its public output shows the ship actor's `actor_type` and any waiver. The informational checks (`Lane`, `Quality`, `Repository standards`, `Automated review`, `Security review`, `Ship`) show progress.

Auto-merge in GitHub is not used.

### Release-affecting PRs and security review

The release-affecting set lives in a **versioned policy file** that fails closed (a file it cannot evaluate makes the PR release-affecting). It includes at least: `VERSION`, release metadata, `RELEASING.md`, every `.github/workflows/**`, `outside-ci.yml`, `CODEOWNERS`, `.gitattributes`, `.gitignore`, `templates/community/**`, governance, standards and release scripts, the `REPOS` list and profiles, lockfiles and dependency manifests, ruleset configuration, the release-affecting policy file itself, the service repository and both runner repositories. For such PRs:
- the review adds a security pass;
- `security_ok` is required from a `security` team member, through the button or a `/security-ok` comment, bound like ship. That person must not have **pushed** any commit in the PR (push ledger) and must never be the ship actor;
- if the Maintainer-agent App pushed anything, ship must come from a human who did not push, by the button or native review;
- no waiver.

## Downgrade and quarantine

Quarantine is stored in the service, not in labels. It attaches to any of: a **PR**, a **principal** (account or App), a **head SHA**, a **tree SHA**, or an **adoption lineage**. Triggers:
- `/downgrade <reason>` from a maintainer or the security lead (principal quarantine is security lead or owner only);
- a push-ledger sender outside the trusted set on a trusted PR;
- membership, team or installation webhooks showing a trusted principal lost its role, or the App was suspended;
- the hourly reconciliation finding a mismatch between live roles and the trusted set.

Effects take place at once and fail closed, even if the audit write fails: affected PRs become outside, every ship, security approval and waiver in the current generation is revoked and tombstoned, pending merge permits are voided, the `Governance` check is set to failure, queued and running paid jobs are cancelled, and adoption of quarantined heads, trees or principals is refused. Opening the same head or tree in a new PR, or adopting it, inherits the quarantine. Only the owner or the security lead can lift a quarantine with `/restore-lane <reason>`, and the restore must name the scope it lifts. Earlier authorizations are never restored.

**Demotion runbook (kept)**: membership events can be delayed or missed, so the operations rule stays: run "revoke all decisions by X" (one service command) **before** demoting or removing a maintainer. The merge-permit re-check and hourly reconciliation are the backstop. Revocation is prompt, not instantaneous.

## Risk tiers and rollout stages

**Tiers** describe what a change touches; lanes describe who made it. Both apply. The **tier classifier** (G9) is deterministic rules only, with no model scoring: it runs in the service from webhook and API data, reads its rules from a versioned policy file on the **base** branch, takes the maximum over all changed files and the size rules, re-runs on every new head, and fails closed to **T3** (an error, an unreadable policy file, a truncated or unparsable file list, or a file count at the API's page cap). Agents can never lower a tier; any human can raise one. Sizes count added plus deleted lines, excluding generated files listed in the policy file (for size only, never for path rules). It is built in stage M0 (G18); until it is live, every PR is T3. The tier, the rule ids that fired and the policy version are audited.

| Tier | Rule |
| --- | --- |
| T0 docs | the inert-lane rules, and at most 300 changed lines |
| T1 low | product source and tests only; at most 400 changed lines (at most 250 outside tests), at most 10 files, one package; no T2 or T3 path; no dependency or lockfile change |
| T2 medium | anything not T0, T1 or T3, including 401 to 1,000 lines, cross-package changes, public API surface, persistent data formats, configuration kept out of the inert lane, and site sources |
| T3 high | any T3 path at any size, more than 1,000 lines, or a PR the classifier cannot evaluate |

The T3 paths, listed exactly in the policy file: the release-affecting set; dependency manifests, lockfiles and toolchain files, and every dependency-update bot PR; authentication, credential and keyring code; execution, sandbox, worker, package-install and agent-write-approval code; network trust (provider endpoints, HTTPS rules, relay and remote control); deployment surfaces (deployment configuration files, distribution, desktop-app capability, permission and content-security-policy files, registry migrations); secrets handling; and agent skill files that grant tools or permissions; plus symlinks, submodules, binaries, mode changes and renames into or out of a T3 path. An adopted PR is at least T2. Release-affecting PRs are always T3 and keep their extra pass and security approval.

The tier sets the reviewer's input cap (G10: T0 32,000, T1 64,000, T2 128,000, T3 160,000 tokens; never above 180,000) and the worst-case reservation. A review that comes back `incomplete` at a tier's cap fails closed.

**Rollout stages** M0 to M5 are the lab's throughput ramp, set by owner decision: M0 is backlog clearance with preflight and shadow; M1 starts after the `.github` pilot; M2 has every governed repository cut over; M3 to M5 raise volume step by step. A stage moves up only by a recorded owner decision. Each stage has a prepaid reviewer balance and ledger cap (G1, see Budget).

**No separate model-session security review in this pipeline** (owner clarification, 2:15 PM PT): a separate model-session security review applies only to work the owner does directly with the owner's own assistant. Pipeline PRs get tests, the automated review on the chosen provider and the owner's ship (plus human security approval where release-affecting). The pipeline has no such extra gate, cost or capacity; G2 and G13, which scoped that pass and its limits, are withdrawn.

## Automated reviewer outcomes

| Outcome | Meaning | `Automated review` |
| --- | --- | --- |
| passed | authenticated payload and successful job, valid, complete, no blocking findings | success |
| blocked | valid, complete, blocking findings | failure |
| incomplete | `complete: false`, invalid or missing payload, input clipped at the cap | failure |
| unavailable | a 429 positively identified as a rate limit or allowance window, a 5xx or outage, or a step timeout | failure, reason code |
| misconfigured | 401, 403, blocked key or team, any other or unidentified 4xx, install hash mismatch, an unmet provider condition | failure; never waivable |
| budget | service reservation refused, 402, exhausted prepaid credit, or a provider policy-budget rejection | failure; never waivable |
| paused | kill switch on | failure |

**Provider error classifier**, one fixed order for every provider: authentication and authorization failures → `misconfigured`; payment-required, exhausted credit or policy budget → `budget`; positively identified rate limit or allowance window, 5xx, timeout → `unavailable`; anything else → `misconfigured`. The chosen provider does not document the status for exhausted credit, so a rejection that is not positively identified as a rate limit is never `unavailable`, and the service ledger's own balance view also yields `budget` when credit is used up. Only `unavailable` can make a PR waiver-eligible.

**Retries**: the service keeps a durable due-time queue. After `unavailable`, it schedules one retry 15 minutes later. When the retry is due, the service atomically claims it, re-validates every gate (open, non-draft, lane, generation, quarantine, dedupe key, budget), and only then dispatches to runner `main`. A nightly sweep retries `unavailable` and `budget` PRs once each, if budget allows. `/review` from a maintainer creates one recorded retry authorization for the current generation. Manual Actions re-runs are refused (first attempt only).

**Waiver**: only the pinned owner, only through the service's owner page. The page uses GitHub OAuth bound to the pinned account id, checks that two-factor authentication is enabled, has CSRF protection, keeps sessions under 15 minutes, requires a passkey step-up registered with the service for each waiver (OAuth alone cannot force a fresh credential entry), and records the session id in the audit record. Comment commands and tokens are not accepted, so neither agents nor the Chief of Staff can waive. It is eligible only when the latest outcome in the current generation is `unavailable`, no valid review result exists for that generation, and the PR is trusted (not inert, outside, adopted or release-affecting). The page offers **"Waive review and ship"** as one action. Each waiver writes an audit record and opens a follow-up issue so the head is reviewed when the reviewer is back. If that later review is blocked, the issue is escalated to the security lead.

So an outage never passes silently (success needs a valid result or a named, eligible waiver), and it never blocks without a next step.

Step timeout: 9 minutes up to 2,000 changed lines, 14 minutes up to the 12,000-line cap. The job timeout is the step timeout plus 3 minutes.

## Budget and cost controls

- **Unit**: one *pass* is one billable reviewer call. One *review* is 2 passes (3 when release-affecting).
- **Atomic reservation** in the service before each pass, against all of these limits: 12 passes per PR per day, 40 per principal per day, 120 per organization per day. A single principal may use at most 40% of the organization limit, so others always have capacity. At most 2 concurrent passes per organization and 1 per principal.
- Cancelled, failed and timed-out passes count.
- **Kill switch**: the owner or security lead can pause all paid review instantly (outcome `paused`).
- **Monthly dollar cap: hard, equal to the current stage balance, per calendar month (UTC)** (decision 1 as amended by G1): $50 in stage M0, then $125, $325, $625, $975 and $1,525 for M1 to M5 (stages under "Risk tiers and rollout stages"). The amounts are re-set after the first 50 reviewed PRs from measured cost. A stage change is an owner decision made only through the owner page (OAuth bound to the pinned account id, passkey step-up, audited) and stored in service state; never from a repository file, comment or label. The ledger cap changes only from that record, and a lowered cap governs at once, even if the provider balance is above it. One service ledger covers every provider and key. How it holds with the chosen prepaid provider, stated plainly:
  - **The provider balance alone is not a monthly cap.** A prepaid balance caps what can be spent before someone buys more; carried-over credit or a mid-month purchase could otherwise take one month's spend past the cap.
  - The cap holds because of four things together: **auto top-up is off** and the invoiced limit is $0; **only the owner can buy credit**, being the only administrator of the dedicated provider team; **a purchase may never take the provider balance above the stage cap** (each purchase is at most the cap minus the current balance), so the balance is also a hard ceiling on total spend; and **the service ledger** counts, per calendar month, every credit purchase including fees and every pass's spend.
  - **Every paid pass goes through the ledger**: legacy replacement, shadow (which does make paid passes), pilot and production. The ledger is deployed before the first paid call of the legacy replacement job (see Migration); at start it imports the current month's provider usage, purchases, fees and any outstanding calls. There is no paid path outside it apart from the held, verified old-key overlap (Migration).
  - **Reservation rule**: a reservation is granted only if, for every calendar month the pass could be billed in, settled spend + outstanding worst-case reservations + the next reservation <= the stage cap, and the month's recorded purchases including fees <= the stage cap. Otherwise the outcome is `budget` (never waivable). A purchase that breaks the purchase rule stops paid review as `budget` and alerts.
  - **Month boundary**: calendar month in UTC, as the provider bills it. Spend is attributed to the provider's billable usage month from the usage read-back, not to the month a reservation was made. A reservation made within the maximum pass duration plus 30 minutes of month end holds capacity in both months until its billed month is known. Work queued but not dispatched by month end expires and is re-reserved in the new month.
  - **Weekly reconciliation**: purchases and the balance are read back from the provider's billing API, or, where no read API exists, from a signed owner and security lead attestation that expires after 30 days. Per-key usage is read back daily (whether the provider exposes per-key usage is verified in preflight 7; if it does not, every pass is `misconfigured` until one key per scope is used and settlement runs on team totals); usage that matches no reservation is settled into its billed month and alerted. An unrecorded purchase is added to its month. An expired attestation or a failed read-back makes every pass `misconfigured`. A monthly comparison with the provider's usage export pauses paid review on any shortfall.
  - **Alerts**: the service notifies the owner and the security lead at 50% and 80% of the cap (the provider's own warning covers only top-ups).
  - **Worst-case bound per pass**: from a reviewed, policy-versioned price table for the pinned model: maximum input (the tier's input cap plus prompt) and maximum output, times the engine's maximum internal attempts, at the provider's higher-tier rate if the input could reach that tier. Each service retry (15-minute retry, nightly sweep, `/review`) is a new pass with its own reservation.
  - **Settlement**: a reservation is replaced by the provider-reported charge for that pass in its billed month. If the charge cannot be determined, the worst-case amount stays charged.
  - **Fail closed**: an unknown model, missing price entry or unbounded request is refused as `misconfigured`.
  - If the gateway is ever used, its fixed fee is counted as settled spend in the month it is charged, and its overage toggle must stay off; discovery of overage on stops its calls as `misconfigured`. Operating with overage on is not part of this design.
- The Actions budget stays.
- Debug refusal: before any reviewer key is placed into any step environment, a pass fails as `misconfigured` if `runner.debug == '1'` or `RUNNER_DEBUG` is set. (`ACTIONS_STEP_DEBUG` and `ACTIONS_RUNNER_DEBUG` are secrets or variables, not environment variables; debug re-runs are already refused by the first-attempt rule.)
- The reviewer installs from a full lock with hashes (`--require-hashes`), or from an image pinned by digest. Actions are pinned by full SHA.
- **No raw output in public**: runner logs print counts and verdicts only, and the reviewer writes its output to a temp file that is never printed or uploaded, on every path. No review-result artifact is uploaded; results reach the service only. The review runner is private, so this rule is defense in depth.

**Reviewer input and output hygiene**: the PR body and comments are passed to the reviewer only as marked untrusted data, never as instructions. The reviewer has no tools and no network access other than the model provider. Every published text field (title, reason and any other text) is NFKC-normalized and stripped of control, zero-width and bidi characters, HTML and HTML entities, images and command-like code fences; `@` mentions (including team mentions), `#123` and `org/repo#1` references, and all links including scheme-less autolinks and bare domains are neutralized; after normalization each title is capped at 120 characters, each reason at 600, and the published review body at 4,000. `file` is published only if it is in the PR's changed-file list, and `line` only as an integer inside that file's hunks. A reviewer verdict is never enough on its own: a human ship is always required.

**Finding publication** is automated, with no human step. The service checks the bounded result against the schema and publishes each non-security finding as a PR review from the App. **Every security finding is held** (decision 13, security lead answer B4): any finding whose category is security, that cites a CWE, or that matches a security keyword list, at any severity and in every lane. Held findings go to a private draft repository security advisory, created with the Governance App's repository security advisories write permission. A failed delivery is retained durably in the service, retried and alerted to the owner and security lead, and never published. The PR shows only a neutral notice, "N finding(s) held for maintainer review", which never reveals file, line or class.

## Outside lane

### What runs, and when

- **Outside CI** (`outside-ci.yml` in each product repo, new): `pull_request`, read-only token, no secrets. GitHub's approval for outside contributors' runs applies (preflight verifies the effective setting per repo). It is for contributor feedback only.
- **Triage** runs in the service from metadata and a bounded diff. It runs automatically, is not subject to fork-run approval, and never executes code.
- **Same-repository branches from untrusted pushers** are prevented by keeping write access to the permitted writers only, with org base permission `read`, and any other writer is detected and alerted (see settings). If one appears anyway, it is outside, and outside CI's run approval does not cover it, so the service ignores its CI.

*Can a non-maintainer bypass the outside lane by pushing a branch to the repository instead of a fork?* No. Lanes are decided by principals (author, every push-ledger sender, live trusted-set membership), not by where the head lives, so that PR is outside. Its branch workflows run without approval, find no stored secret, confer nothing even with a raised built-in token, and cannot publish (see "Branch workflows confer nothing, and cannot publish"). Controls: write access limited to the permitted writers, the access alert, rulesets on `main`, `contrib/**`, all tags and `workflow-pins/*`, and the Actions budget.

### Triage rules

Triage re-runs on open, push, edit (title, body or base), and linked-issue changes, debounced to 2 minutes:

| Rule | Default |
| --- | --- |
| Size (checked from PR metadata **before** fetching the diff) | at most 30 files, 1,000 changed lines, 256 KB of diff, 10 metadata pages |
| File types | no `.github/**`, no symlinks, binaries, executables, lockfile-only or vendored changes, no new dependencies |
| Linked issue | for larger changes: an open issue in the same repository labelled `accepted` by a maintainer (scope approval), or a maintainer accepting the scope on the PR itself. Exempt: at most 50 changed lines, no new dependencies and no public API change, with a problem statement in the PR. Maintainers label new issues `accepted` or `declined`, with a reason, within about 5 business days |
| PR template | all structured sections answered (see below) |
| Sign-off (DCO) | required in every lane (decision 21): `Signed-off-by` matching each commit author. The triage comment explains the fix (`git commit --amend -s` or `git rebase --signoff`) |
| Rate | at most 2 open PRs per contributor per repo, and 5 new PRs per contributor per day across the org |
| Event caps | at most 20 triage evaluations per PR per day, 50 per principal, 500 org-wide. When exceeded, label `triage:paused`; a maintainer resumes |

Results go into the decision log, keyed by head and **metadata revision** (a hash of title, body, base and linked issues). One bot comment is edited in place. Account age and history are shown as context and never close a PR on their own.

### Anti-slop bar (both lanes)

The PR template is the same for both lanes, and `Repository standards` checks it in both:
- **Problem**: a link to an issue or discussion, or a one-paragraph concrete problem for trivial fixes.
- **Change**: what changed and why, scoped to the problem.
- **Validation**: commands run and their result. Must contain at least one command or test name.
- **Regression evidence**: the test that fails before and passes after, or "not applicable: <reason>".
- **Generated content**: none / partial / substantial, and what it covered.
- **Attestation**: "I have read and can explain every changed line."

Generated content is allowed if it is disclosed and meets the same bar. No generation detector is used. The disclosure says what was generated, never which tool. Disclosure never counts against a PR, and a missed disclosure is fixed by editing the PR, not by closing it. The DCO sign-off covers generated portions (the right to submit them, and no incompatible third-party code), and CONTRIBUTING states inbound = outbound licensing. The disclosure is kept in the adoption record as provenance. The Maintainer-agent App's PRs carry the same visible disclosure, and the shipping human certifies them (see Ship). Low-effort criteria for maintainers and triage, judged on content:
- formatting-only, comment-only or rename-only churn without an accepted issue;
- the same diff opened across several repositories;
- tests that do not exercise the changed code;
- a validation section that does not match the diff;
- dependency or version bumps from outside contributors.

Triage flags the mechanical ones. Maintainers judge the rest, using the reviewer guidance in CONTRIBUTING.

### Spam and appeals

Only promotional or link content closes a PR as spam. The PR is labelled `spam`, closed and locked, and the comment links the appeal path (the Discussions Appeals category or the SUPPORT address). A cross-repository duplicate burst, or more than double a rate or event cap, is not spam: the PR gets `triage:paused` or `needs-work`. The spam rules are published in CONTRIBUTING. Automation never blocks accounts.

**Appeals**: Discussions with an Appeals category and the SUPPORT address are enabled and confirmed before cutover. An appeal gets a response within about 5 business days, from a different maintainer than the one who closed the PR where one exists. Reopening is recorded.

**Stale**: a community PR still failing triage after 14 days of waiting on the contributor (time waiting on maintainers does not count) gets a friendly comment and is closed with "reopen any time".

Public wording, in CONTRIBUTING and bot comments: "maintainer PRs" and "community PRs" (never "trusted" and "outside"), a one-line reason (fork PRs never get secrets or paid review until a maintainer adopts them), and an explicit welcome for first-time contributors.

### Adoption: the only path to paid review

`/adopt` (button or comment, bound like ship) by a maintainer is accepted only if every triage rule passes for the **current head and metadata revision**, and nothing in scope is quarantined. The service then:
1. pushes that exact head, unrewritten, to `contrib/<repo>-<pr>-<n>`. Rulesets let only the Governance App create or update `contrib/**`;
2. records the adoption (origin PR, head, tree, metadata revision, adopter, disclosure and sign-off evidence) in the log;
3. opens a trusted-lane PR from the Maintainer-agent App, marked adopted, keeping the contributor's commit authorship where possible and crediting each contributor with `Signed-off-by` and `Co-authored-by` trailers in the body that becomes the squash message, and carrying the disclosure and sign-off evidence;
4. closes the original with a link, and comments "landed as #N, thanks @handle" on it when the adopted PR merges.

The Maintainer-agent App opens the adopted PR but never ships it (decision 6).

Any PR whose head is in `contrib/**` must match an adoption record for that exact head, or it is outside. Adopted PRs are never inert and never waivable, and they always get the full review. Later contributor pushes need a new `/adopt`, which creates a new head and generation.

## Branch protection, rulesets and settings

- **Preflight decides the form**: an organization ruleset if the plan supports it, otherwise one ruleset per repository (expected to be available on public repositories; verify).
- Rules on `main`: ruleset A and ruleset B as in the credential matrix section. No native approval count, except the code-owner backstop on `.github`, both runner repositories and the service repository (code-owner review from `@ejmlabs/security`, no bypass).
- **No emergency bypass** (decision 7): no owner bypass and no break-glass ruleset. During a service outage, merges wait for the service. Revisit at retirement.
- `contrib/**`: ruleset A forbids force push and deletion only; ruleset B restricts creation and update to the Governance App. All tags: creation, update and deletion restricted to the governed release actor. `workflow-pins/*` keeps its current immutable rules.
- **Guarded cutover** per repository, only after preflight passes (decision 15): (1) the new rulesets are added while legacy branch protection is still present, so both apply and merges pause briefly; (2) effective rules are read back (`/rules/branches/main`) and must show exactly ruleset A with no bypass actors and ruleset B with only the Governance App, plus the App binding of `Governance`; (3) the legacy branch protection is removed; (4) effective rules are read back again. A durable per-repository cutover record is written at step 3. Rollback runs the same steps in reverse and records a rollback epoch. There is never an unprotected interval.
- `configure_repositories.py` gains ruleset read-back and checking, App installation checks and `ejm-chess` support. It keeps the existing writer audit, now checked against the permitted writers.
- **Write-access alert**: any principal not on the permitted-writer allowlist with write or higher on a governed repository is a finding. Signals:
  - humans and teams (direct or outside collaborator, team grant): `member`, `membership`, `team` and `team_add` webhooks, plus reconciliation;
  - deploy keys with write: `deploy_key` webhook (needs repository deployments read), plus reconciliation;
  - other Apps with contents write: **reconciliation only**, because installation webhooks reach only the receiving App. The hourly job reads the organization's App installation inventory (organization administration read) and each installation's repository coverage. An incomplete or forbidden inventory read is itself a finding.

  The settings tool runs the same checks in preflight and at every cutover. Each finding writes an audit record and notifies the owner and the security lead. PRs whose author or push-ledger sender is a flagged principal are outside regardless. A deploy-key or App-inventory finding makes every PR in that repository outside, because the push sender cannot tell those credentials apart. The service only alerts; it never removes access. Removing access is an owner action, and preflight does not pass while a finding is open. With the intended installation (permitted writers only), preflight reports no findings.

## Release validation migration

`release.py` changes together with the cutover. It selects the evidence format **before** verifying, from the durable per-repository cutover record: legacy evidence only for merges before that repository's cutover or inside a recorded rollback epoch; new evidence for every other merge. It never falls back to legacy evidence when a service lookup fails. New evidence:
- the release commit is a squash merge by the Governance App of exactly one PR;
- the merge commit carries a `Governance` evidence check run from the Governance App's integration id, published right after the merge (and by the sweep if a crash interrupted it). Its output holds the decision record id, PR, head, generation, ship actor, security approver when release-affecting, review result ids and policy version. `release.py` verifies these through the service's read-only evidence endpoint, and fails if the service is unreachable or the check is missing;
- tree check: the release tree equals the **merge tree the service validated**, not the PR head tree;
- release-affecting merges must show `security_ok`.

The legacy path is removed only after an end-to-end release passes on the pilot repository.

## Audit

One JSON record is written per decision: `ts, repo, pr, generation, epoch, head, base, lane, actor_id, actor_type, decision, reason_code, run_id, policy_version`. Records never contain comment bodies, model output or secrets. They are stored in the service's append-only store; a mirror to a private repository is optional (supported on the Team plan). A weekly anomaly report goes to the security lead.

**Retention and access** (decision 22): maintainer decision records are kept 2 years; community-contributor records 12 months, unless tied to an open security case or another recorded legal or security hold. Ordinary deletion is refused for every actor. Expiry is a separate, narrowly authorized retention operation run by the service only: it deletes expired records and their identifying ledger links in the store, mirrors and backups (backups expire on the same schedule), and writes a deletion record that contains no expired personal data. Read access: the owner, the security lead and the Board. A public privacy note (in CONTRIBUTING and `GOVERNANCE.md`) says what is recorded, who reads it, how long it is kept, and how contributors can request their own records. Quarterly, aggregate counts of waivers, quarantines, held findings and spam closes are published.

**Failure rule**: revocations (unship, downgrade, quarantine, dismissal, edits or deletions, pause) apply first and always, and their audit records are queued durably in the same transaction as the revocation and retried until stored. While the audit queue has a backlog, **new** authorizations (ship, security_ok, waiver, adopt, restore), merge permits and merges are refused, with "audit unavailable, retry".

Preflight 13 reads back its owner id, repository selection, permissions and expiry; if the org's settings do not allow such a token or any of these cannot be read back, the exception is not used and the `ejm-ui` lift and restore stay with the owner in person;
- **separate restore runner**: the credential is held only by the automation's restore runner, a deterministic process with no model in its loop, in a store and environment that the orchestrator's shell and sandbox, the service, every runner, the Maintainer-agent and Chief of Staff Apps and every other automation cannot read; never printed or logged. The runner alone makes every call with the credential. The orchestrator, an agent that reads untrusted `ejm-ui` PR content, can only send it a request of `ejm-ui`, a PR number and an action (lift, merge, restore or lock); it supplies no body, path, head or credential;
- **allowlisted operations**: the runner builds every call itself and refuses any other before it is made, by an allowlist of method, path and body digest, for `ejm-ui` only: the lift (the required-status-checks update with the saved `checks` less the automated-review context), the merge (that PR, squash, with the head the service verified passed as `sha`), the restore (the saved `checks` with their `app_id` through the required-status-checks update), the lock (a `PUT` of the saved JSON with `lock_branch: true`) and the protection reads for its read-backs. Bodies are built by `scripts/branch_protection.py` from the saved JSON in the service's durable store whose digest the service recorded before the lift; the PR and head come from the service's record, not from the request (row 52). A required-signatures difference is not repaired by the runner: it locks and pages, and the owner repairs it in person;
- **deadline restore**: a durable job of the restore runner, separate from the run that made the lift, armed and read back before the lift; at 6 minutes 30 seconds it reads `main`'s protection and, if the context is still missing, restores, or locks if the restore fails, and reads back, so a clean restore is in place before the monitor's first read at 7;
- **logged with read-back**: every lift, merge, restore and lock by the automation writes an audit record (repository, PR, call, protection JSON before and after, field-by-field read-back result, times, the authenticated login with the runner's run id and host, the 4:53 PM PT authorization) to the governance audit store;
- **page on every use**: the restore runner pages the owner on every lift, merge, restore and lock, with its read-back result; the security lead is copied as witness. The outside monitor does not see a use as such: it pages when its own reads at 7 and 8 minutes differ from its pre-window read and on any change outside a registered window, so a failed or falsely reported restore, or a use with no window, reaches the owner even if the runner's page does not;
- **while it lasts**: the owner's comment commands and native reviews do not count anywhere the service is authoritative; the hourly reconciliation and the monitor flag any `ejm-ui` protection change or `main` commit not matched to a registered window, a legacy gate run or a logged exception merge (row 51); the service's post-window comparison pages on any protection difference from the saved JSON; the owner's web audit-log review after each use compares every action under the owner's account with the log;
- **removed at expiry**: at the end the restore runner's copy is deleted, the owner revokes the token (GitHub's expiry ends it by 2026-11-20 in any case), a call with it is shown to fail, the runner refuses by clock, and the owner's audit-log review of the whole period is recorded and countersigned by the security lead once a second human exists (row 53). Until all of that is read back, expiry is incomplete and an incident.

## Risks / trade-offs

- **New infrastructure**: the service is a new component to host and secure. That cost buys PR-scoped authority, App-only merges and private state, which commit checks and comments cannot provide.
- **Service outage stops merges** (fail closed). There is no bypass (decision 7); revisit at retirement.
- **Quality runner logs are public**; it holds no secret and runs no paid review. The review runner is private.
- **Prepaid provider**: the provider balance alone is not a monthly cap; the cap depends on auto top-up staying off, the owner being the only team administrator, the purchase rule and the service ledger, which every paid pass uses from the first legacy replacement call.
- **Interim secrets in product repositories**: the old key (legacy name) until each switch re-pin (dated deadlines; branch-readable, accepted), then the switch's key until each cutover or 2027-01-31.
- **Old-action spend during the overlap**: bounded by verified, held old-key limits with no further purchases; each hold persists past revocation and the deadline until settlement is complete.
- **Two re-pins per pinned repository** (V, then S), because each installed validator checks callers exactly.
- **Reservation OIDC exception**: product-repository tokens accepted for reservation grants only, with exact claims, until cutover or 2027-01-31.
- **Removal depends on the ledger**: the ledger, and so hosting, must be live before step 1's deadline; otherwise repositories freeze at their deadlines.
- **Named exception to decision 7**: per qualifying re-pin PR, one scripted lift of only the automated-review context (at most 10 minutes on the script's own exit paths, with a durable saved protection and an independent deadline page at 7 to 8 minutes from the service and a monitor outside it, armed first) with a service-generated, digest-verified diff and a single-commit check; expires 2026-11-20 or at the last re-pin; never covers V or S.
- **Crash restore** (owner, 4:35 PM PT; no App holds administration write): a crash during a lift leaves the automated-review requirement off on that repository until the restore, with the branch lock as the fallback: on `ejm-ui` the automation's deadline restore at 6 minutes 30 seconds, elsewhere (and if that fails) the owner's manual restore after the 7-to-8-minute page; other required checks, paused agent merges and the single-commit check bound it.
- **Named exception to decision 11** (owner, 4:53 PM PT, accepted): until 2026-11-20 at the latest, the lab's automation holds an owner credential for the `ejm-ui` lift and restore and can act with the owner's administrator rights on `ejm-ui` (accepted at full width); narrowed by the required fine-grained token to `ejm-ui` and the listed permissions, held by a restore runner with no model in its loop that makes only allowlisted calls, detected by the outside monitor, the exception log and the owner's audit-log review, and removed at expiry.
- **Detection on Team**: no audit-log streaming or API; the events listed as lost in "Detection on GitHub Team" are seen only in the owner's web audit-log review.
- **Second human for the security role** is a hard prerequisite for preflight; rollout waits for it.
- **Legacy statuses forgeable until cutover** by a branch workflow with `statuses: write` (pre-existing); forging is a policy violation and reconciliation flags it on frozen repositories.
- **Package publication and pre-existing releases**: a trusted human's branch workflow can publish a package or a release on an existing tag (decision-14 residual); releases published before immutability was enabled are inventoried.
- **Compromised maintainer account**: accepted risk (decision 14), including a trusted human's branch workflow creating a draft release or a release on an existing tag (immutable releases stop changes to published ones).
- **Administrator bypass on the private review runner**: not blockable on Team; accepted, with detection.
- **Diff-only engine chosen without a pilot**: review quality is measured in shadow and the pilot before cutover.
- **Agent shipping is off permanently** (decisions 6, 11). One action per merge stays a human action.
